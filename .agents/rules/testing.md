# 自動テストルール (Testing Rules)

AIエージェントと開発ユーザーの二人体制において、開発スピードの向上とデグレード（先祖返り・バグ混入）の防止を両立するため、自動テストの実装と実行に関するルールを定義します。

---

## 1. 基本方針：テストファースト＆テスト必須化
* **ルールの要旨**: テストコードのない機能実装やバグ修正は「未完了」とみなす。
* **具体的アクション**:
  1. 新規APIエンドポイント、新規共通コンポーネント、または重要なビジネスロジックを追加する際は、必ず対応する自動テストコードを同コミット内に含めること。
  2. バグを修正した際は、まずそのバグを再現するテストコードを作成し、修正後にテストがパスすることを確認する（回帰テストの作成）。
  3. AIエージェントが実装を行った後は、報告前に必ず関連するテストコマンドを実行し、**テストがすべてパスしていることを確認・報告する**こと。

## 2. バックエンド（Laravel）のテスト設計
* **ルールの要旨**: データベースの整合性とセキュリティ（マルチテナント隔離）を確実にテストする。
* **具体的アクション**:
  1. **セキュリティ（テナント隔離）テストの必須化**: 
     - Aテナントのユーザーでログインした状態で、Bテナントの在庫IDを指定してAPI（詳細・更新・削除）を呼び出したとき、`404 Not Found` が返却されることをテストで実証する。
  2. **バリデーションテスト**: 
     - 不正なパラメータ（値の欠落、範囲外の数値、不正な型）を送信した際に、適切に `422 Unprocessable Entity` が返却され、エラーメッセージが含まれることを検証する。
  3. **トランザクション＆ロックテスト**: 
     - 在庫の加減算ロジックにおいて、同時実行や不正な残高マイナスが発生しない境界値テストを作成する。

## 3. フロントエンド（React / TypeScript）のテスト設計
* **ルールの要旨**: ユーザー操作に伴う状態遷移と、APIエラー時の挙動（楽観的UIのロールバック等）をテストする。
* **具体的アクション**:
  1. **カスタムフックとロジックのテスト**:
     - 在庫の計算ロジック、データ整形ロジックなど、UIから分離された純粋なロジックは単体テスト（Vitest等）で網羅する。
  2. **楽観的UIとロールバックのシミュレーション**:
     - APIリクエストが失敗（500や422等）した際、UIが一度楽観的に更新された後、正しくエラーメッセージが表示され、元のデータにロールバックされる状態変化をテストする。
  3. **コンポーネントのモックテスト**:
     - MSW (Mock Service Worker) 等を活用してAPI通信をモック化し、ローディング・成功・失敗の各状態におけるUIのレンダリングが正しいことを検証する。

## 4. テスト実行環境とコマンド
* **ルールの要旨**: テストを迅速に実行できる環境を維持する。
* **具体的アクション**:
  1. コマンドラインからワンコマンドで全テストを実行できる状態を維持する。
     - バックエンド: `docker-compose exec backend php artisan test` (Docker環境下の場合) または `php artisan test`
     - フロントエンド: `npm run test` または `npx vitest run`
  2. データベーステストは、インメモリ（SQLite `:memory:`）またはテスト用の隔離されたDBスキーマを使用し、本番および開発用データを破壊しないこと。
