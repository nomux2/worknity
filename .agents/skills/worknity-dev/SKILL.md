# Worknity プログラム修正・開発スキル (`worknity-dev`)

Worknity のプログラム修正・機能追加・UI改善・リファクタリングを行う際は、以下の **5大原則** と **ステップバイステップの手順** を厳수してください。

---

## 5大原則（絶対遵守）

1. **推測で勝手に進めない（`/grill-me` 徹底）**
   - 仕様・要件・UI挙動・エッジケースに少しでも曖昧さや複数の選択肢がある場合、**自己判断で実装を開始してはならない**。
   - 必ず先に設計書（`_doc/`）と既存コードを調査し、残った意思決定ポイントを **`ask_question` ツールで1問ずつ、推奨案 `(Recommended)` 付きで質問** し、ユーザーと完全に合意してから着手する。
2. **キオスクモードのUI/UX原則**
   - **全画面キオスクスタイル**: 画面全体を `100vh` 固定（ブラウザ全体の縦スクロール禁止、`overflow: hidden`）とし、一覧テーブル等の大量データ領域のみをコンテナ内スクロール（インナースクロール）で制御する。
   - **ゼロ・コンテキストスイッチ**: ページ遷移で作業を分断させず、2ペイン構成・インライン展開・スライドパネル等で1画面完結させる。
   - **客席・現場キオスク端末対応**: セルフ操作画面（`/catalog` 等）ではヘッダーを隠し、解除にはテンキーによるパスワード認証（`KioskUnlockModal`）を必須とする。
3. **PCに詳しくない人でも迷わない「究極のシンプルさ」**
   - **専門用語の排除**: 画面上のラベル・ボタン・エラー通知にIT用語や難しい業務用語（マスタ、アロケーション、トランザクション、マルチテナント等）を出さず、直感的な日常表現（「棚卸」→「数を合わせる」等）にする。
   - **キーボード入力の最小化**: 可能な限り文字入力をさせない。テンキーUI、`+`/`-` 増減ボタン、ワンタップ選択、カメラによるバーコード読取など、タッチ操作だけで完結させる。
   - **シングルパス＆誤操作防止**: 1画面・1領域につきプライマリボタンを原則1つに絞り、すべてのタップ領域は **最小 `44px × 44px` 以上** を確保する。
4. **React / Laravel のデファクトスタンダード設計**
   - 詳細基準は [references/react-laravel-standards.md](./references/react-laravel-standards.md) を参照。
   - **React**: Viewとロジックの分離（カスタムフック `hooks/` への切り出し）、1コンポーネント200行以内、`any` 禁止・厳格な型定義（`types/`）、共通UI（`components/ui/`）の活用、楽観的UIと失敗時ロールバックのペア実装。
   - **Laravel**: Thin Controller（バリデーションは `FormRequest`、ビジネスロジックは `Services/` へ分離）、`Multitenant` トレイトによるテナント隔離、他テナントアクセス時の `404 Not Found` 隠蔽、在庫更新時の `DB::transaction()` + `lockForUpdate()`。
5. **厳格なテストファースト（TDD: Red → Green → Refactor）**
   - 本番コードを書き始める前に、**必ず失敗するテストコード（バグ再現テストまたは新仕様の検証テスト）を先に作成・実行（Red）** する。
   - テストがパスする最小限かつ本質的な実装を行い（Green）、コードを整理した上で全テスト・型チェック・Lintをパスさせる（Refactor）。

## プログラム修正・開発の実行手順

### Step 1: 設計書（`_doc/`）と現状コードの調査
1. 関連する設計書（`_doc/基本設計書.md`、`_doc/API定義書.md`、`_doc/データベース設計書.md`、`_doc/機能/<機能名>/`）を読み、仕様を把握する。
   - ※設計書の変更が必要な場合は、`doc-sync` スキルを併用して設計書を先に更新する。
2. 修正対象のフロントエンド（`apps/main-app/src/`）およびバックエンド（`backend/app/`）のコードと既存テストを確認する。

### Step 2: `/grill-me` インタビューによる仕様合意
コード調査で解決できない仕様の分岐・UI表現・エッジケースがある場合：
1. **1度に1問ずつ**、`ask_question` ツールを使ってユーザーに確認する。
2. 各質問には必ずエージェントとしての客観的な評価と **`(Recommended)` 推奨選択肢** を先頭に提示する（アンチパターンや複雑すぎる案には代替案を提示する）。
3. すべての疑問点が解消し、修正方針が確定するまで本番コードを変更しない。

### Step 3: テストファースト（Red フェーズ）
本番コードを編集する前に、対象領域のテストを先に追加・更新する。
- **バックエンド (`backend/tests/Feature/`)**:
  - 正常系だけでなく、**別テナント（別 `organization_id`）からのアクセス時に `404 Not Found` になること**、**不正入力時に `422` になること**、および境界値（在庫マイナス防止等）のテストを含める。
- **フロントエンド (`apps/main-app/src/**/*.test.tsx`)**:
  - ユーザー操作による表示変化、APIエラー時のロールバック、タッチ操作UIの挙動を検証するテストを含める。
- テストを実行し、意図通り失敗すること（Red）を確認する。

### Step 4: 本番コードの実装（Green & Refactor フェーズ）
以下のチェックリストを満たすように実装する：
- [ ] [キオスクUI＆シンプルUXチェックリスト](./references/kiosk-ux-checklist.md) の全項目を満たしているか？
- [ ] [React / Laravel デファクトスタンダード基準](./references/react-laravel-standards.md) に準拠しているか？
- [ ] `// TODO` や仮置きモックデータ、マジックナンバーを残していないか？

### Step 5: 一括検証スクリプトの実行と完了報告
実装完了後、付属の検証スクリプトを実行してテスト・型チェック・ビルドのすべてがパスすることを確認する。

```bash
bash .agents/skills/worknity-dev/scripts/verify.sh
```

すべてのチェックがパスしたことを確認した上で、変更したファイル・関数へのクリック可能なリンクを添えて日本語で簡潔にユーザーへ報告する。
