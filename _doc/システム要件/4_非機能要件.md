# システム要件：4. 非機能要件・UX原則

本書は、ミニマリスト業務管理システム「Worknity（フェーズ1）」におけるユーザビリティ設計（認知負荷の排除）、機能拡張コントロール（いつでもやめられる仕組み）、セキュリティ、および信頼性・保守性に関する非機能システム要件を定義する。

---

## 1. ユーザビリティ（認知負荷の排除）

「ユーザーに考えさせない、迷わせない」ことを最優先とするUX原則を定義する。

### 1.1. ミニマリズム設計
* **画面要素の最小化：**
  * 各画面に配置するボタン、入力フィールド、テキスト表示は、主要タスクの実行に絶対に必要なものだけに厳選する。
  * 「あれば便利かもしれない」程度の補助機能や装飾的なグラフィックは原則として排除する。
* **入力フォームのステップ数削減：**
  * 在庫のイン出庫や棚卸操作は、キーボードのみ、あるいはモバイル端末での「タップ数最小（3タップ以内推奨）」で完結するインタラクションにする。

### 1.2. シンプルな動線（ログイン即操作）
* **初期設定のゼロ化：**
  * 新規登録やログインの完了直後に、チュートリアルや複雑なプロフィールの登録画面、拠点登録などのステップを挟まない。
  * ログイン後は直接、在庫一覧と操作（入庫・出庫・棚卸）が統合されたメイン画面へ遷移する。これにより、ユーザーはログインしてすぐに実業務を開始できる。

### 1.3. フロントエンド・パフォーマンス
* **SPA（Single Page Application）の高速起動：**
  * Viteによる適切なアセットバンドリング、不要な外部ライブラリの排除を行い、初回ロード時間（LCP - Largest Contentful Paint）を **2.0秒以内** とする。
* **画面遷移の快適さ：**
  * SPAによるクライアントサイドルーティングを採用し、ページ遷移時のローディング（白画面）を発生させない。
  * バックエンドAPIのレスポンス時間は、通常処理時で **100ms〜200ms以内** を目標値とし、インジケーター（スピナー等）を見せる必要がない速度を目指す。

## 2. 機能拡張コントロール（いつでもやめられる仕組み）

将来の有料化や機能追加時において、ユーザーの心理的・金銭的負担を最小限に抑える機能コントロール要件。

### 2.1. アドオン機能管理（プラグイン形式）
* **コア機能の不変性：**
  * 今後追加される高度な機能（例：GPS打刻、複数倉庫管理、バーコードスキャン等）は、システムのコアコードを複雑化させないよう、アドオン（プラグイン）形式で実装する。
* **アドオン管理画面のUI/UX：**
  * 管理者は、カード形式で並んだアドオン一覧から、トグルスイッチのON/OFFだけで各機能の有効化・無効化を切り替えられるようにする。

### 2.2. 簡易な契約コントロール
* **無料体験のワンタップ開始：**
  * 有料アドオン機能の試用時、「14日間無料体験を開始」ボタンをクリックするだけで、クレジットカード情報の事前入力を求めることなく、即座に機能が試用できる仕様とする。
* **「1秒解約」の実現：**
  * 契約内容の解約や機能の無効化を希望するユーザーに対し、アンケートの強制回答や、過度な引き留め画面、何重もの「本当に解約しますか？」といったポップアップの提示を禁止する。
  * 「解約（無効化）する」ボタンまたはトグルのワンクリックで、その場ですぐに契約無効化処理が完了する導線とする。

## 3. セキュリティ要件

マルチテナントSaaSとして、顧客データを保護するためのセキュリティ最低要件。

### 3.1. 通信・データ保護
* **HTTPS/TLSの強制：** `SSL/TLS 1.2` または `1.3` でのみ通信を許可する。安全でない古いプロトコル（SSL 3.0, TLS 1.0/1.1）はサーバー側で遮断する。
* **パスワードの暗号化：** パスワードは必ず十分に強力なハッシュ関数（Bcrypt または Argon2id 等）を使用し、ストレッチングを施した上でデータベースに保存する。

### 3.2. 脆弱性対策
* **SQLインジェクション対策：**
  * データベースへの問い合わせには、ORM（Eloquent）を使用するか、プレースホルダーを用いたプリペアドステートメントを例外なく使用する。生のSQL文字列結合によるクエリ構築は厳禁とする。
* **XSS（クロスサイトスクリプティング）対策：**
  * ユーザーからの入力値（商品名など）を画面に描画する際は、フロントエンドのテンプレートエンジン（React等）による自動エスケープを機能させ、不正なスクリプト実行を防止する。
* **CSRF（クロスサイトリクエストフォージェリ）対策：**
  * JWT認証の場合はステートレスな運用となるが、Cookie等を用いてトークンを連携する場合は `SameSite=Strict` や `Secure` 属性、およびCSRFトークンの検証を組み合わせる。

## 4. 可用性・信頼性・保守性

### 4.1. バックアップ要件
* **定期バックアップ：** データベース内の全データについて、最低1日1回（利用頻度の低い深夜帯を推奨）の自動フルバックアップを別領域（同一物理サーバー外、またはクラウドストレージ等）に生成・保存する。バックアップは過去30日分保持する。

### 4.2. ログ管理・監視
* **アプリケーションエラーログ：** システムエラー（500エラー等）発生時、バックエンドは詳細なスタックトレースをログファイルに出力し、管理者が検知・分析できるようにする（ただしログ内に生のパスワードやJWTを含めないようにマスキングする）。
* **在庫履歴ログ（監査ログ）：**
  * 在庫の「誰が」「いつ」「何を」「どれだけ」「入庫/出庫/棚卸したか」という操作ログを、在庫マスタとは別テーブル（例: `stock_logs` 等、フェーズ2以降に本格導入予定）に記録する仕組みを検討する。

### 4.3. 保守性（コード品質）
* **静的型付けの導入：** フロントエンドの開発には TypeScript を標準採用し、開発時の型安全性とリファクタリングの容易性を確保する。
* **PSR（PHP Standard Recommendation）規約：** バックエンド（PHP）コードは `PSR-12` などのコーディング規約に厳密に従い、コードの可読性と一貫性を維持する。
