# システム要件：6. ロール・権限設計

本書は、ミニマリスト業務統合サービス「Worknity（フェーズ1）」におけるシステム全体のロールベースアクセス制御（RBAC / Role-Based Access Control）、権限定義、および実装仕様を定義する。

---

## 1. 基本方針

本システムはマルチテナント（複数組織）構成であり、ユーザーの組織に対するアクセス権限は組織（テナント）単位で独立して制御される。

* **テナント毎のロール設定：**
  * ユーザーのロール（権限）は `organization_user`（組織メンバーシップ中間テーブル）に紐づく。
  * これにより、同一のログインユーザー（同一 `user_id`）であっても、組織Aでは「管理者（`admin`）」、組織Bでは「スタッフ（`staff`）」といった異なる権限を割り当てることができる。
* **状態（Status）による実行制御：**
  * アカウントの状態（有効: `active` / 一時停止: `suspended`）も組織単位で制御し、一時停止中のユーザーは該当組織のデータに一切アクセスできないようにする。

---

## 2. ロール（権限）定義

フェーズ1では、以下の2つの組織内ロールを定義する。

| ロール名 | 物理名 | 説明 | ユーザー管理権限 |
| :--- | :--- | :--- | :--- |
| **管理者** | `admin` | 組織のオーナー、店長、代表者など。組織設定、スタッフ管理、全データ操作、請求管理を行う。 | **フルアクセス**（閲覧・追加・編集・削除・一時停止） |
| **スタッフ** | `staff` | 現場の作業員、アルバイトなど。日々の現場業務（在庫の入出庫や打刻等）を行う。 | **アクセス不可**（他ユーザーの情報や組織設定は閲覧も不可） |
| **ゲスト** | `guest` | 外注先、外部パートナー、納品業者など。登録や更新は行えず、開示された特定情報のみを閲覧する。 | **アクセス不可**（他ユーザーの情報や組織設定は閲覧も不可） |

* **将来の拡張（プラットフォーム運営者）：**
  * システム全体のテナント管理、請求プラン変更、メンテナンス等を行う **システム運営者（`super_admin`）** ロールは組織（テナント）の外で定義し、別の管理画面からアクセス制御を行う設計とする。

---

## 3. 機能・画面別 権限マトリクス

システムで提供される各機能・APIエンドポイントに対するアクセス権限は以下の通り定義する。

| 大機能 | 小機能・アクション | APIエンドポイント例 | admin | staff | guest | 備考 |
| :--- | :--- | :--- | :---: | :---: | :---: | :--- |
| **認証** | ログイン・ログアウト | `/auth/login`, `/auth/logout` | ◯ | ◯ | ◯ | 全ロール共通。 |
| | 組織の切り替え | `/auth/organization/switch` | ◯ | ◯ | ◯ | 所属組織への切り替えのみ。 |
| **ユーザー管理** | スタッフ一覧の取得 | `GET /users` | ◯ | × | × | スタッフ・ゲストは閲覧不可。 |
| | スタッフアカウントの追加 | `POST /users` | ◯ | × | × | adminの組織IDが自動付与。 |
| | ロールや状態（status）の変更 | `PUT /users/{id}` | ◯ | × | × | adminのみ操作可能。 |
| | スタッフの削除（所属解除） | `DELETE /users/{id}` | ◯ | × | × | adminのみ操作可能。 |
| **在庫管理** | 在庫一覧の閲覧 | `GET /stocks` | ◯ | ◯ | △ | ゲストは特定共有在庫のみ閲覧可能（5.4項）。 |
| | 新しい商品の追加 | `POST /stocks` | ◯ | ◯ | × | ゲストは商品登録不可。 |
| | 在庫の入庫・出庫・棚卸 | `POST /stocks/{id}/inflow` 等 | ◯ | ◯ | × | ゲストは在庫操作不可。 |
| **発注管理** | 自社宛て発注データ一覧の閲覧 | `GET /orders` | ◯ | ◯ | △ | ゲストは自社担当発注分のみ閲覧可能（5.4項）。 |
| | 発注の新規登録・変更 | `POST /orders` | ◯ | × | × | 管理者のみ。 |
| **勤怠管理** | 出勤・退勤の打刻（現場用） | `/attendance/stamp` | ◯ | ◯ | × | ゲストは打刻不可。 |
| | 自身の勤務履歴の閲覧 | `/attendance/me` | ◯ | ◯ | × | ゲストは勤怠管理の対象外。 |
| | 全スタッフの勤務履歴管理 | `/attendance/admin` | ◯ | × | × | 管理者のみ。 |
| **契約・設定** | アドオン機能の有効化/無効化 | `/settings/addons` | ◯ | × | × | 管理者のみ。 |
| | 請求情報の確認・解約手続き | `/settings/billing` | ◯ | × | × | 管理者のみ。 |

## 4. 安全保護ルール（最後の管理者の保護）

システム内に管理権限を持つアクティブなアカウントが皆無になり、組織全体の操作ができなくなる「セルフロックアウト」を防止するため、以下の安全ルールをバックエンドおよびフロントエンドで強制する。

* **ルール：** 組織内に所属する「有効（`status = active`）かつ `admin` ロール」のユーザーが **1名のみ** の場合、そのユーザーに対する以下の操作はすべてAPIレベルで却下し、エラー（`422 Unprocessable Entity`）とする。
  1. 権限ロールを `staff` へ降格させる操作。
  2. アカウント状態（`status`）を `suspended`（一時停止）にする操作。
  3. 組織から削除（所属解除）する操作。

---

## 5. 実装方針

### 5.1. フロントエンド（React / SPA）
* **ルーティングガード：**
  * ルーター（React Router）のメタデータに `requiresAdmin: true` を設定し、ログインユーザーのロールが `admin` でない場合、`/users` や `/settings` などの管理画面へのアクセスを遮断し、リダイレクトさせる。
* **動的表示制御（Conditional Rendering）：**
  * ユーザーのロールと状態を React Context や状態管理ライブラリで保持する。
  * スタッフ（`staff`）ログイン時には、管理者用ボタンやサイドメニュー項目を表示しない（DOM自体にレンダーしない）。
  * 最後の管理者の場合、自身の操作行のトグルスイッチやプルダウンを非活性（`disabled`）にする。

### 5.2. バックエンド（Laravel / API）
* **ミドルウェアによるロールチェック：**
  * APIルート定義において、管理者専用のエンドポイントには `CheckRole:admin` ミドルウェアを適用する。
    ```php
    Route::middleware(['auth:api', 'role:admin'])->group(function () {
        Route::post('/users', [UserController::class, 'store']);
        Route::put('/users/{id}', [UserController::class, 'update']);
        Route::delete('/users/{id}', [UserController::class, 'destroy']);
    });
    ```
  * 一般スタッフからのリクエストに対しては、即座に `HTTP 403 Forbidden` を返却する。
* **アカウント一時停止のチェック：**
  * 認証ミドルウェアは、JWTのトークン検証時に該当ユーザーの該当組織におけるメンバーシップ状態（`status`）をデータベースで問い合わせ、`suspended` の場合は有効なトークンであっても `HTTP 401 Unauthorized` を返却してセッションを破棄する。

### 5.3. AI（MCP：Model Context Protocol）連携時の制限
* 将来導入するAIエージェントがMCPエンドポイント（`/mcp/v1/tools/call`）を介してシステム操作を行う際も、リクエストを行ったユーザー（JWTから特定）のロールをそのままバックエンドが検証する。
* AIエージェントに管理者権限を間接的に奪取されないよう、管理者専用ツール（例: スタッフ追加や設定変更）を実行する際は、フロントエンド側で明示的な **「実行承認ダイアログ（Human-in-the-loop）」** を挟み、管理者の承認クリックを必須とする。

### 5.4. ゲスト向けの情報開示制限（データフィルタリング）方針
* ゲストロール（`guest`）のユーザーに対し、情報漏洩を防ぎつつ特定のデータのみを閲覧させるため、バックエンドAPIはリクエスト時に以下のデータフィルタリングロジックを強制する。
  * **共有在庫のフィルタリング：**
    * ゲストユーザーが在庫一覧（`GET /stocks`）を要求した際、テーブルの `attributes`（JSON型）等に含まれる公開フラグ（例: `{"is_shared": true}`）が真である商品レコードのみを返却する。
  * **発注データ（注文書）のフィルタリング：**
    * ゲストユーザー（外注先担当者等）が所属する企業・取引先コード（例: `vendor_id`）を `users` マスタまたは中間テーブルに保持する。
    * 発注データ取得時、バックエンドはクエリに `WHERE organization_id = :org_id AND vendor_id = :user_vendor_id` による絞り込みを自動適用し、該当外注先向けに発注された注文書レコードのみを返却する。これにより、他社への発注データや全社集計などの機密データへのアクセスを遮断する。
