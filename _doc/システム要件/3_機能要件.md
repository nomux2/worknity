# システム要件：3. 機能的システム要件

本書は、ミニマリスト業務統合サービス「Worknity（フェーズ1）」における認証・ユーザー管理、在庫管理（コア機能）、および将来のためのAI（MCP）連携機能の詳細なシステム要件を定義する。

---

## 1. 認証・ユーザー管理

マルチテナント環境下におけるセキュアなユーザー認証および管理者によるスタッフ追加フローを定義する。

### 1.1. JWT（JSON Web Token）マルチテナント認証
セッション状態をサーバー側で保持しないステートレスな認証機構を採用し、システムの可用性と拡張性を高める。

* **トークン発行仕様：**
  * バックエンドは、ログインAPI（`POST /api/v1/auth/login`）の認証成功時にJWTを発行・署名する。
  * **署名アルゴリズム：** `HS256`（対称鍵暗号）または `RS256`（非対称鍵暗号）を使用。鍵情報は環境変数で管理する。
  * **JWT ペイロード（Claims）構成：**
    ```json
    {
      "iss": "https://api.worknity.jp",
      "sub": "1234567890",              // ユーザーID (users.id)
      "company_id": "987654321",        // 所属企業ID (companies.id)
      "role": "admin",                  // 権限 ('admin' または 'staff')
      "iat": 1717084800,                // トークン発行時刻
      "exp": 1717088400                 // トークン有効期限（例：発行から1時間）
    }
    ```
* **フロントエンドでのトークン保持と通信方針：**
  * **メモリ内保持：** セキュリティリスク（XSS攻撃によるトークン窃取）を極小化するため、フロントエンド（React）はJWTを `localStorage` や `sessionStorage` には保存せず、JavaScriptのメモリ（React State または Context / Redux等）上でのみ保持する。
  * **APIリクエスト時の付与：** HTTP通信時、リクエストヘッダに `Authorization: Bearer <JWT>` を付与する。
  * **画面リロード（F5等）時の対応：** メモリ上のJWTがクリアされるため、セキュアCookieを用いたサイレントトークンリフレッシュ機構、または自動再ログイン処理をバックエンドと連携して実行する。

### 1.2. 管理者によるユーザー追加フロー（アプローチA）
新規にサービスを申し込んだテナントに対して、自律的なユーザー管理機能を提供する。

1. **初期管理者の自動作成：**
   * 企業が「Worknity」の利用登録（アカウント作成）を行った際、システムは自動的に `companies` レコードを生成し、その企業に紐づく最初のユーザーとして `role = 'admin'` （管理者）のアカウントを1件自動作成する。
2. **スタッフ追加機能（管理者向け）：**
   * 管理画面において、`admin` 権限を持つユーザーのみがアクセスできる「ユーザー追加フォーム」を提供する。
   * **入力項目：** 「表示名 (name)」「メールアドレス (email)」「初期パスワード (password)」
   * **バックエンド処理：**
     * リクエストを送信した管理者のJWTから `company_id` を抽出する。
     * 新規登録する `users` レコードの `company_id` に対し、抽出した管理者の `company_id` を自動で割り当てる。
     * `role` は一律で `'staff'` を設定する（スタッフが勝手に管理者へ昇格するのを防ぐため）。
     * パスワードはバックエンドでセキュアにハッシュ化（Bcrypt等）した上で保存する。

## 2. 在庫管理（コア機能）

本システムのコアとなる在庫変動処理について、整合性と排他制御を担保する仕様を定義する。

### 2.1. 在庫操作（イン出庫・棚卸）の定義
* **入庫（Inflow）：**
  * 指定された商品（`stocks.id`）に対し、数量を加算する。
  * **仕様：** `新数量 = 現数量 + 入力数量`
  * **バリデーション：** 入力数量は 1 以上の整数とする。
* **出庫（Outflow）：**
  * 指定された商品に対し、数量を減算する。
  * **仕様：** `新数量 = 現数量 - 入力数量`
  * **バリデーション：**
    * 入力数量は 1 以上の整数とする。
    * **負数在庫の許容ポリシー：** フェーズ1では、実在庫がマイナスになる出庫（`現数量 < 入力数量`）は、原則としてバリデーションエラー（「在庫数が不足しています」）として却下する。ただし、業務上どうしてもマイナス入力を許容する必要がある場合は、テナントの設定（`companies.attributes` 等）で制御可能とする仕様を検討する。
* **棚卸（Stocktake / Overwrite）：**
  * 指定された商品の数量を、入力値で完全に上書きする。
  * **仕様：** `新数量 = 入力数量`
  * **バリデーション：** 入力数量は 0 以上の整数とする。

### 2.2. 多重更新（レースコンディション）対策
複数ユーザーが同時に同一商品の在庫を更新した際（例: 2人が同時に同一商品を「1個出庫」した場合）、データの不整合（ロストアップデート）を防ぐ。

* **トランザクション排他制御：**
  * 在庫の加減算処理を行う際、バックエンドは必ずデータベーストランザクションを開始する。
  * 対象行を取得するクエリにおいて **`SELECT ... FOR UPDATE` (悲観的ロック)** を発行し、更新処理が完了するまで他プロセスによる該当行の読み込み・更新をブロックする。
  * 処理完了後、変更内容をコミットし、ロックを解放する。

## 3. AI（MCP：Model Context Protocol）連携

将来的にAIエージェントがシステムを操作・検索するための、MCP（Model Context Protocol）に準拠したAPI設計方針を先行実装する。

### 3.1. MCP エンドポイント仕様
バックエンドは、一般のAPIルートとは別に、以下のエンドポイントを実装する。

#### ① `POST /mcp/v1/tools/list` （提供ツールの定義リスト返却）
AIエージェントに対して、Worknityで実行可能なアクション（ツール）の定義をJSON Schema形式で返却する。

* **返却するツールリストの例：**
  * `get_stock_list`（在庫一覧の取得）
  * `adjust_stock`（入庫・出庫・棚卸の実行）
* **レスポンス構造例：**
  ```json
  {
    "tools": [
      {
        "name": "adjust_stock",
        "description": "在庫の入庫、出庫、または棚卸を行います。",
        "inputSchema": {
          "type": "object",
          "properties": {
            "product_name": { "type": "string", "description": "商品名" },
            "operation": { "type": "string", "enum": ["in", "out", "overwrite"], "description": "操作種別 (in: 入庫, out: 出庫, overwrite: 棚卸)" },
            "quantity": { "type": "integer", "minimum": 0, "description": "数量" }
          },
          "required": ["product_name", "operation", "quantity"]
        }
      }
    ]
  }
  ```

#### ② `POST /mcp/v1/tools/call` （AIからの命令実行）
AIエージェントからのリクエストボディに基づき、実際の在庫更新ロジックを呼び出す。

* **処理フロー：**
  1. 受信したリクエストデータからツール名とパラメータをパースする。
  2. ログイン中ユーザーの `company_id` に属する在庫データを対象に、指定された操作（入庫/出庫/棚卸）を実行する。

#### ③ `POST /mcp/v1/resources/list` （AI向け安全なリソース開示）
AIエージェントが読み取り可能なシステム内の「コンテキスト（在庫一覧やログなど）」を返却する。

* **セキュリティ制約：** 返却するデータは、呼び出し元のJWTで認可された `company_id` に紐づくデータに厳密に制限される。

### 3.2. セキュリティおよび誤操作防止（Human-in-the-loop）
AIエージェントによる誤った在庫更新や、悪意あるプロンプト注入（インジェクション）による意図しない大量変更を防ぐためのセーフガード。

* **API認証の強制：** 全ての `/mcp/v1/*` エンドポイントへのアクセスには、クライアントアプリから発行された有効なJWTトークンを必須とする。
* **実行確認UI（人間の介在）：**
  * AIエージェントが `tools/call` を呼び出して在庫を更新する前に、フロントエンド（またはチャットインターフェース）上に「実行確認カード」を生成する。
  * **仕様：** 「AIが『A商品の在庫を5個減らす（出庫）』ことを提案しています。実行しますか？ [承認] [却下]」のようなUIを表示し、人間のオペレーターによる明示的なクリック（承認）がない限り、データベースへの物理的な書き込み処理（コミット）を行わない構成とする。
