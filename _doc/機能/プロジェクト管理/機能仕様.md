# プロジェクト管理 機能仕様書

本書は、ミニマリスト業務統合サービス「Worknity」におけるプロジェクト管理機能のビジネスルール、権限、および詳細な仕様を定義するものである。

---

## 1. 機能概要

プロジェクト管理機能は、特定の組織（テナント）において、現場、案件、または特定の目的ごとにタスクをグループ化し、全体の進捗や工数を一元管理するための機能である。
土建業の「現場」や、製造業の「案件」など、複数タスクの集合体として業務を可視化したいユーザー向けに提供される。

---

## 2. アクターと権限

本機能を利用できるアクターと権限は以下の通りである。

* **管理者 (`admin`)**:
  - プロジェクトの作成、編集、削除。
  - プロジェクト全体の進捗状況の確認。
  - 他のスタッフへのプロジェクト割り当て。
* **一般スタッフ (`staff`)**:
  - 自組織内のプロジェクト一覧の閲覧。
  - 自身が割り当てられた（または関与する）プロジェクトの詳細確認。
  - プロジェクトに紐づくタスクの登録・更新。

---

## 3. ユースケースと詳細仕様

### 3.1. プロジェクト一覧の閲覧
* **説明：** ログインユーザーは、自組織（テナント）に登録されているプロジェクトの一覧を閲覧できる。
* **表示項目：**
  - プロジェクト名
  - 現在のステータス（未着手 / 進行中 / 完了 / 保留）
  - 期間（開始日〜終了予定日）
  - 全体進捗率（％）
  - 予定工数合計 / 実績工数合計（時間）
* **セキュリティ（データガード）：**
  - クエリ実行時、必ず `organization_id` による絞り込みを強制し、他組織のプロジェクトが一切表示されないようにする。

### 3.2. プロジェクトの新規作成
* **説明：** 管理者は、新規プロジェクトを登録できる。
* **入力項目：**
  - プロジェクト名（必須）
  - 概要・詳細説明（任意）
  - 開始予定日（任意）
  - 終了予定日（任意）
  - 予算・想定工数（任意）
* **仕様：**
  - 作成したプロジェクトには、作成した管理者の `organization_id` が自动的に付与される。
  - 初期ステータスは「未着手（`planned`）」として作成される。

### 3.3. プロジェクト情報の編集・ステータス更新
* **説明：** 管理者（および許可されたユーザー）は、プロジェクトの情報や進行ステータスを更新できる。
* **ステータス遷移仕様：**
  - `planned` (未着手) ➔ `active` (進行中) ➔ `completed` (完了)
  - 任意の状態で `suspended` (保留/中断) に移行可能。
* **自動完了連動（オプション）：**
  - 将来的な拡張として、プロジェクト内の全タスクが「完了」となった際に、プロジェクトのステータスを自動的に「完了」に移行する、または移行を促すアラートを表示する。

### 3.4. プロジェクト進捗率の動的計算
* **説明：** 各プロジェクトの進捗率（％）は、紐づくタスクの状況からリアルタイムに算出する。
* **算出ロジック：**
  - $\text{進捗率（％）} = \left( \frac{\text{完了済みのタスク数}}{\text{プロジェクト内の総タスク数}} \right) \times 100$
  - 総タスク数が0の場合は `0%` とする。
  - 小数点以下は四捨五入して整数で表示する。

### 3.5. プロジェクトの削除
* **説明：** 管理者は、不要になったプロジェクトを削除できる。
* **仕様：**
  - プロジェクトを物理削除または論理削除した場合、紐づいていたタスク（`tasks` テーブル）の扱いは以下の通りとする。
    - **基本仕様**: 紐づいていたタスクは削除せず、`project_id` を `NULL` に更新して「プロジェクトなし（単発タスク）」として維持する。
    - **理由**: プロジェクトが終了または削除されても、タスクの実行履歴やコメント（作業ログ・申し送り）は組織のデータ資産として残す必要があるため。

---

## 4. ビジネスルールとバリデーション

### 4.1. 入力バリデーションルール
1. **プロジェクト名：**
   - 必須入力。
   - 最大文字数：100文字。
   - 同一組織内でのプロジェクト名の重複は許容する（同名の異なる案件が存在し得るため）。
2. **日付（開始予定日・終了予定日）：**
   - 開始予定日および終了予定日は、有効な日付フォーマット（`YYYY-MM-DD`）であること。
   - 「開始予定日 ≦ 終了予定日」の整合性を満たすこと。

---

## 5. セキュリティとデータガード設計

1. **他テナント存在の隠蔽 (404 Not Found)：**
   - `GET /api/v1/projects/{id}` などのAPIにおいて、指定された `id` のプロジェクトが存在しない場合、または別テナント（`organization_id` が異なる）のデータである場合は、一律 **`404 Not Found`** を返却する。
   - 悪意あるユーザーがプロジェクトIDを総当たりして他組織のプロジェクトの存在や名称を推測することを完全に防止する。

2. **マルチテナントデータガードの継承：**
   - プロジェクトに関するすべてのクエリ（一覧取得、詳細取得、更新、削除）には、グローバルスコープによる `WHERE organization_id = ?` の自動適用を強制する。
