
# 1. システム概要

小規模事業者や個人事業主の「人・物・金」にまつわる業務の「複雑さ・面倒さ」を極限まで排除し、認知負荷ゼロで日々の運用を継続できる、ミニマリストな業務統合サービス（マルチテナント型SaaS）。

初期フェーズでは、あらゆる特化型サービスの共通土台（コア）となる「超シンプルなユーザー・企業管理」**および**「入出庫・棚卸に絞った在庫管理」の基盤を、最速で立ち上げることを目的とする。

---

# 2. 開発・インフラ方針（フェーズ1）

* **サーバー構成：** 開発初期のコストと管理の手間を最小化するため、**Xserver（1台）** を使用。
* **ディレクトリ構造：** 1つのリポジトリで管理する **モノレポ（Monorepo）構成**。
* `/apps/main-app/` : フロントエンド領域（ReactによるSPA）
* `/backend/` : バックエンド領域（Laravel等、単一のデータベース）


* **将来への仕込み（拡張性）：**
* データベース接続や環境依存情報は `.env`（環境変数）で完全管理し、将来のDBサーバー分離を容易にする。
* フロントとバックエンドは、最初からサブドメイン（例: `app.worknity.jp`, `api.worknity.jp`）を分けてURLを独立させる。
* バックエンド側に、将来のAIサーバー接続を見据えた **MCP（Model Context Protocol）の通信窓口** をあらかじめ定義しておく。



---

# 3. データベース要件（必要最小限）

データはすべて1つのデータベースで統合管理する。将来の「食品倉庫特化」などの横展開（項目追加）に耐えられるよう、拡張性を考慮した設計とする。

### ① 組織マニフェスト（`organizations` テーブル）

* すべてのデータの最上層となる「組織・グループ」の箱。
* *保持項目:* `id`, `name`（組織名、チーム名、グループ名、または屋号）

### ② ユーザー（`users` テーブル）

* 1つの `organization_id` に対して「1対多」で紐づく。
* *保持項目:* `id`, `organization_id`, `email`, `password`（ハッシュ化）, `role`（権限：`admin` または `staff`）

### ③ 在庫（`stocks` テーブル）

* ユーザー単位ではなく、`organization_id` に直接紐づく。これにより複数人でのリアルタイム共有を可能にする。
* *保持項目:* `id`, `organization_id`, `product_name`, `quantity`, `attributes`（**JSON型：将来の賞味期限や温度帯などの特化型オプション用の拡張枠**）

# 4. 機能要件

## 4.1. 認証・ユーザー管理機能

* **マルチテナント認証：** ログイン成功時、バックエンドはユーザー情報と `organization_id`、`role` を含んだ **JWT（アクセストークン）** を発行。フロント（React）はページ遷移（SPA）を挟んでもこのトークンをメモリ上に保持する。
* **管理者によるユーザー追加（アプローチA）：**
* サービス申込者が自動的に `admin`（管理者）となる。
* 管理者は「ユーザー一覧画面」から、スタッフの「名前」「メールアドレス」「初期パスワード」を入力してその場でスタッフを追加できる。
* 追加されたスタッフには、管理者と同じ `organization_id` と、一律で `staff` 権限が自動付与される。



## 4.2. 在庫管理機能（コア機能）

* **2-Pane Systemによる統合操作画面：** ページ遷移を完全に排除し、右ペインに「マスター在庫一覧（2/3幅）」、左ペインに「アクション領域（1/3幅）」を固定配置したゼロ・コンテキストスイッチ画面。
* **イン出庫・棚卸・履歴のワンストップ実行：**
  * **入出庫 (Inbound / Outbound)：** 右ペインクリックで左ペインの伝票シートに行を追加し、数量入力後に一括確定。入出庫のデータフロー方向を示す `→` / `←` ベクトルアニメーションを表示。
  * **棚卸 (Stocktake)：** 右ペインをロック＆半透明化し、左ペインのスプレッドシート風シートで実在庫を入力。Enterキーで確定して次の行へ自動フォーカス移動。不一致行は3色判定（一致：白、不足：青、過剰：赤）で右ペインに反映され、異常行（不足・過剰）は最上部へ自動ソート。
  * **履歴 (History)：** 選択された商品の変動ログ（日時、数量変更、担当者）を時系列でタイムライン表示。
* **データガード：** バックエンドはすべてのデータ操作時、トークンから抽出した `organization_id` と一致するデータのみを処理対象とし、他組織データへのアクセスを物理的に遮断する。

## 4.3. 将来のためのAI（MCP）連携仕込み

* バックエンドのルーティングに、将来別サーバーとして導入するAIエージェントがシステムを操作・検索するための、MCP規格に準拠したAPIエンドポイント（受け皿）を先行して定義する。
* `POST /mcp/v1/tools/list` （AIにシステムができること[入出庫等]を伝える窓口）
* `POST /mcp/v1/tools/call` （AIからの命令でデータベースを更新する窓口）
* `POST /mcp/v1/resources/list` （AIに現在の在庫状況を安全に渡す窓口）


* **セキュリティ：** AI側からこのMCPエンドポイントを叩く際も、ユーザーのJWTトークンを必須とし、権限外のデータ操作や、確認なしの一発登録を防ぐ設計（確認カードの挟み込み）を前提とする。

---

# 5. 非機能要件・UX原則

* **認知負荷の徹底排除：** 「設定」や「入力フォーム」を極限まで減らし、迷わせない導線にする。
* **いつでもやめられる安心感：** 今後追加する有料機能（例: GPS打刻オプション等）は、アプリストアのようなカード型UIで「ボタン一発で14日間無料体験」「1秒で無効化（解約）」ができる導線とする。
